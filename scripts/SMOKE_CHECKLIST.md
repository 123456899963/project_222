# 茶·图鉴 —— 浏览器人工冒烟清单

> 用途：在「提交 / 发版 / 大改」前，用真实浏览器人工过一遍核心链路，验证「发现茶 → 看详情 → 收藏/写笔记/分享」与「多清单、投稿审核」是否完好。
> 性质：**手工点验清单**，不引入 Playwright 等自动化依赖；逐项打勾并记录结果。
> 覆盖：登录与核心浏览、S9 多清单、S10–S13 投稿审核、分享链路。
> 记录方式：发现问题复制到 [build-log](../harness/build-log.md) 或缺陷台账，注明浏览器与日期。

---

## 0. 环境前置检测（先跑这步）

在 PowerShell 中逐项确认，全部通过后再开始点验：

```powershell
# 1) 后端健康（应返回 200，且非统一业务体）
try { (Invoke-WebRequest http://127.0.0.1:8000/api/v1/health -UseBasicParsing).StatusCode } catch { "后端未启动" }

# 2) 前端首页可达（应返回 200）
try { (Invoke-WebRequest http://127.0.0.1:5173 -UseBasicParsing).StatusCode } catch { "前端未启动" }

# 3) 前端代理转发正常（/api 由 5173 转发到 8000）
try { (Invoke-WebRequest http://127.0.0.1:5173/api/v1/health -UseBasicParsing).StatusCode } catch { "代理异常" }
```

未启动时按此启动（两个独立终端）：

```powershell
# 终端 A：后端
cd backend; python run.py        # 监听 8000

# 终端 B：前端
cd frontend; npm run dev         # 监听 5173，自动代理 /api 与 /uploads
```

准备两个账号：

| 角色 | 说明 |
|---|---|
| 普通用户 | 通过页面注册 1 个新账号（如 `smoke_user`），用于收藏/清单/投稿 |
| 管理员 | `.env` 中 `ADMIN_USERNAME` / `ADMIN_PASSWORD`（默认用户名 `admin`），用于审核 |

浏览器建议：Chrome / Edge 最新版，开一个**普通窗口**（用户操作）+ 一个**无痕窗口**（游客/被分享者视角）。

## 3. S10–S13 投稿审核链路

> 用普通窗口操作「用户」，管理员窗口操作「审核」。

| # | 步骤 | 操作 | 预期结果 | 结果 |
|---|---|---|---|---|
| 3.1 | 投稿入口 | 用户进「我的清单」→「投稿新茶 / 科普」 | 打开投稿页，双 Tab 可见 | ☐ |
| 3.2 | 茶类矛盾拦截 | 投稿新茶：名称填「碧螺春」，茶类选「红茶」 | 提交即被拦，提示“属于绿茶”类信息，未入队 | ☐ |
| 3.3 | 名称查重拦截 | 投稿与现有茶同名（如「大红袍」） | 提示“过于相似”，未入队 | ☐ |
| 3.4 | 正常投稿新茶 | 填一款不存在的新茶完整信息并提交 | 提示「等待审核」，出现在「我的提交」为 pending | ☐ |
| 3.5 | 投稿科普 | 详情页「投稿科普」，选某茶写 50 字内容 | 提交成功，「我的提交」出现 pending 记录 | ☐ |
| 3.6 | 越权访问 | 用户直接访问 `/admin/contributions` | 被拒（403 或跳登录），看不到审核队列 | ☐ |
| 3.7 | 审核队列 | 管理员进后台「投稿审核」 | 默认 pending，看到 3.4/3.5 两条，带提交人用户名 | ☐ |
| 3.8 | 通过新茶 | 管理员对 3.4 点「通过」 | 状态变 approved；前台列表/搜索可见该新茶且已上架 | ☐ |
| 3.9 | 通过科普 | 管理员对 3.5 点「通过」 | 状态变 approved；目标茶详情页「茶友科普」显示该内容 | ☐ |
| 3.10 | 拒绝 | 用户再投一条，管理员以预设理由「信息不完整」拒绝 | 「我的提交」显示 rejected + 该理由 | ☐ |
| 3.11 | 删除限制 | 用户尝试删除已处理（approved/rejected）记录 | 无删除入口或被拒；仅 pending 可删除 | ☐ |
