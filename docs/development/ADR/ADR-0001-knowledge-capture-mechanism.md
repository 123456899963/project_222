# ADR-0001：建立开发知识沉淀机制

## 1. 背景与问题

项目已有一整套权威文档（PRD、技术栈、架构、数据模型、API 契约、安全、测试、设计），
但这些文档描述的是"最终状态"，不记录**达成过程**：为什么选 Cookie 会话而不是 JWT、
某次接口调整是谁在什么背景下决定的、某个 Bug 为什么反复出现。

结果是：决策依据只存在于对话记录中，跨会话即丢失；同类错误重复出现却没有人补测试或补规则；
接口/数据库变更容易只改代码不改文档。需要一套**低成本、可追溯、不制造文档负担**的沉淀机制。

## 2. 决策驱动因素

- 单人/小团队开发，维护成本必须低，不能要求每次提交都写长篇文档。
- 已有权威文档体系，新增机制不能与之冲突或重复。
- 接口与数据库变更必须可追溯（AGENTS §10 已有要求，但缺少执行载体）。
- 反复出现的错误需要转化为自动化测试或明文规则，而不是靠记忆。
- 项目要求"记录真实结果"，不能出现"文档写已完成、实际没验证"的情况。

## 3. 备选方案

### 方案 A：只写 build-log（单一开发日志）

- 做法：所有变更、决策、测试结果都塞进一份按日期追加的日志。
- 优点：只有一个文件，门槛最低。
- 缺点：决策的"备选方案对比"会被日志流水淹没；半年后难以按主题检索；日志会无限膨胀。

### 方案 B：只建 ADR（决策记录）

- 做法：只记录重要决策，日常任务不留痕。
- 优点：结构清晰，适合沉淀架构取舍。
- 缺点：无法回答"某次改动测了什么、留下什么问题"；接口/数据变更的同步责任缺少落点。

### 方案 C：三层记录（权威文档 + ADR + build-log）

- 做法：
  - **权威文档**回答"是什么"（规则唯一依据）；
  - **ADR** 回答"为什么"（原因、备选方案、最终选择）；
  - **build-log** 回答"做了什么、测了什么、还剩什么"（每任务一条）。
- 优点：职责单一，各取所需；ADR 数量可控，build-log 可流水化；接口/数据同步有明确检查项。
- 缺点：需要纪律约束（交付前必须回填），否则三层都会空转。

### 方案 D：引入外部知识库 / Wiki 工具

- 做法：用 Notion、Confluence 或独立 Wiki 承载。
- 优点：检索与协作能力强。
- 缺点：引入新工具与账号依赖，与"文档随代码走"冲突；MVP 阶段收益不足。

## 4. 最终选择

**选择：方案 C（三层记录）**

理由：

1. 直接对应驱动因素：ADR 控制数量、build-log 保持轻量，二者都不与权威文档争抢"唯一依据"的地位。
2. 方案 A 会让决策对比失真，方案 B 会丢失测试与遗留信息，二者都只解决一半问题。
3. 方案 D 引入外部依赖，违反"最小改动、不新增工具链"的约束，MVP 阶段不划算。
4. 记录随仓库走，可随代码一起 review，符合 SDD 的"证据闭环"原则。

## 5. 影响与后果

**正面影响**

- 重要决策可追溯到原因与备选方案，减少反复讨论。
- 每个任务的测试证据与遗留问题有固定落点。
- 接口/数据库变更有了"必须勾选"的同步清单。

**负面影响 / 需要接受的代价**

- 交付前多一步回填动作；漏填会让机制失效。
- 需要人工判断"是否重要"，存在主观性（已用触发条件表降低歧义）。

## 7. 复审条件

- 出现"漏填 build-log 导致问题无法追溯"的实际案例；
- ADR 数量超过 30 条仍无法按主题检索；
- 团队规模扩大、需要多人并行协作与权限控制；
- 进入第二阶段（S1–S17）后流程复杂度显著上升。
