## 1. 目的与核心原则

### 1.1 目的

把零散的任务请求统一为可追溯、可验收的执行路径，确保：

1. 每行代码都能追溯到明确的需求来源（PRD 条目 / API 端点 / 安全项 / 测试用例）。
2. 业务规则、接口契约、数据库结构、安全控制不被"顺手改掉"。
3. 测试结果、验收结论、文档同步都有实跑证据，不靠口头声明。
4. 只有真正需要人拍板的变更才打扰用户，其余任务按标准流程自驱完成。

### 1.2 核心原则

| 原则 | 含义 |
|---|---|
| **规则前置** | 编码前先确定"依据的是哪一条已确认规则"，找不到来源就停下来，不凭经验补规则 |
| **单一事实源** | 文档冲突时以 AGENTS.md §10 列出的权威版本为准；仍无法判定则升级为 C 类等待确认 |
| **最小改动** | 只做任务要求的改动；不重构无关代码、不格式化无关文件、不引入未确认依赖 |
| **证据闭环** | 测试必须实跑并记录；未运行不得写"已通过"；失败/跳过必须如实标注 |
| **闸门分层** | 流程强度随变更风险分级，A 类直接编码，B 类先方案，C 类必须人工确认 |
| **决策留痕** | 重要取舍写入对应文档的变更记录，并在任务总结中复述 |

## 2. 任务分级与闸门

### 2.1 判定顺序

每个任务开工前按以下顺序判定，**任一步命中即按对应等级执行**，不再看后续步骤：

```
1. 属于 MVP 范围吗？            否 → D 类（不开发）
2. 触碰任何"冻结规则"吗？        是 → C 类（人工确认）
   （PRD 业务规则、权限矩阵、字段约束、API 契约、数据库结构、
     安全控制 S-01–S-33、架构分层、技术栈）
3. 需要跨层/跨模块改动吗？       是 → B 类（先出方案）
   （≥2 层，或前后端同时改，或涉及 ≥3 个文件）
4. 其余                         → A 类（直接编码）
```

> 判定结果写入任务卡（见 §5.1）。分类拿不准时按更高一级执行。

**A/B 唯一边界**：新增或修改**端点、字段、响应行为** = B 类；只改**单层内部**且对外行为不变 = A 类；需要改契约/表结构/安全项/架构 = C 类。禁止把"实现一个新端点"判成 A 类。

### 2.2 分级定义

| 级别 | 名称 | 是否可直接编码 | 必需产出 | 批准人 |
|---|---|---|---|---|
| **A** | 直接实施 | ✅ 可以 | 任务卡（可简写）+ 测试证据 + 变更总结 | 无需批准 |
| **B** | 方案先行 | ⚠️ 先出方案，方案自检通过后编码 | 完整任务卡 + 技术方案 + 步骤拆解 + 测试证据 | 无需人工批准，但方案须在任务输出中可见 |
| **C** | 确认先行 | ❌ 必须等待人工确认 | B 类全部产出 + **变更影响说明** + 用户明确同意 | 用户 |
| **D** | 范围外 | ❌ 不开发 | 一句范围说明（引用 PRD §6 / §2.3） | —— |

### 2.3 A 类：可直接进入编码（项目实例）

| 示例任务 | 为什么是 A 类 |
|---|---|
| 按 `原型/` 与 PAGE_SPECS 调整首页/列表页样式，只改 CSS 变量与 BEM 类名 | 不改变契约、数据、安全与业务规则，视觉依据已冻结 |
| 前端纯函数实现：筛选条件组合、`page_size` 越界夹取、分享 URL 组装 + Vitest | 行为已由 PRD/API 契约规定，仅落地实现 |
| 实现与契约对齐的修正：FastAPI 422 → 400/`40000`、Cookie 属性、字段名 `snake_case` | 文档已规定，属于"实现向文档对齐" |
| 补齐 `backend/app/repositories/` 下的**单个**查询方法，并让既有 Service 调用它 | 五层架构已冻结，属既定待办的单点落地 |
| 修复某条已失败测试的最小代码改动 | 验收标准已有，改动面小且可回归 |
| 文案、注释、文档错别字修正 | 不改变任何对外行为 |

> **不属于 A 类**：新增/修改端点、字段、错误码、响应结构，或改变筛选/分页/排序口径——即使契约已存在，也按 B 类走完整链路方案。

### 2.4 B 类：先输出设计方案再编码（项目实例）

| 示例任务 | 为什么需要方案 |
|---|---|
| 按 API_CONTRACT 实现**单个端点全链路**（schema → repository → service → router → 前端 api/types） | 跨 2 层以上、前后端同时改，需先定分层落点与字段映射 |
| 创建 `core/auth_deps.py`（`get_current_user` / `get_admin_user`）并按 SECURITY 接入各路由 | 横切所有受保护端点，需先列受影响端点清单 |
| `main.py` 注册全局异常处理器并统一错误映射 | 影响全部端点的响应形态 |
| 完整实现一个页面（如 TeaDetailView：组件拆分、状态、请求、错误提示） | 多文件、多状态分支，需先定组件边界 |
| 将 Service 中直连查询批量下沉到 `repositories/` | 多文件重构，需先列迁移清单与回归范围 |
| 按 TEST_PLAN 用例 ID 新增一批 pytest 用例 | 需要先定 fixture/基线数据与断言维度 |
| 补齐前端 Vitest 配置与首批纯函数用例 | 技术栈已定，但涉及构建配置与目录约定 |

> B 类方案必须包含"分层落点 + 契约对齐 + 测试策略 + 回滚方式"，模板见 §5.2。

### 2.5 C 类：必须等待人工确认（项目实例）

| 变更类型 | 具体示例 |
|---|---|
| **业务规则** | 调整品鉴笔记长度上限、分享有效期、茶品下架后的可见范围、收藏清单语义 |
| **权限矩阵** | 管理员是否可一键收藏、游客可见字段范围、注册用户可执行的操作边界 |
| **API 契约** | 新增/删除端点，改请求或响应字段、错误码、分页默认值（`page_size=12`）、排序规则（`id DESC`） |
| **数据库结构** | 增删表/列/索引/ENUM、改字符集或排序规则、任何 Alembic 迁移 |
| **安全控制** | 增删改 S-01–S-33 任一项；实现方式与 SECURITY.md 冲突时的取舍（如 bcrypt cost） |
| **架构分层** | 允许 Router 直查库、合并/新增层、改变模块边界、跨层调用 |
| **技术栈/依赖** | 新增运行时依赖（如 openapi-typescript、APScheduler）、替换 UI 库、改变构建工具 |
| **上线配置** | 轮换 `SECRET_KEY`、关闭 `DEBUG`、修改种子管理员密码策略 |
| **CI/构建流程** | 修改 `.github/workflows/`、发布脚本、测试门禁的关键行为 |
| **越界实现** | 第二阶段 S1–S17、X1–X13 相关能力的"顺手实现" |

C 类任务在方案末尾必须给出**变更影响说明**（影响哪些文档/端点/表/测试/用户可见行为），并明确写出"待确认问题"，得到用户明确答复后才进入阶段 6。

### 2.6 D 类：范围外

PRD §6 的 S1–S17 与暂不实现项 X1–X13 **一律不开发**，包括多清单管理、用户投稿与审核、个性化推荐、7 天热度统计、Docker Compose 等。收到此类需求时：说明范围外 → 若用户坚持，先转为需求变更讨论（C 类），不得直接开工。

### 2.7 执行中的分级升级

编码或测试中发现以下情况，**立即停止编码**，回到阶段 4 并升级为 C 类：

- 需要改契约才能让实现"跑通"；
- 需要动表结构或索引；
- 需要放宽某条安全校验；
- 需要跨层调用才能复用代码；
- 发现文档间冲突且无法按 AGENTS §10 判定。

输出内容：现状 → 为什么必须变更 → 可选方案与推荐 → 影响面 → 待确认问题。

## 3. 十阶段执行流程

### 3.0 总览

| 阶段 | 核心动作 | 必须产出 | 通过判据 |
|---|---|---|---|
| 1 | 明确任务目标和需求来源 | 任务卡（含分级、验收标准） | 目标可验证、来源可引用、范围外已写明 |
| 2 | 阅读相关项目文档 | 已读文档清单与关键条款摘录 | 能说出"依据哪一节/哪条" |
| 3 | 分析现有代码和影响范围 | 影响面清单（层/文件/测试/文档） | 无遗漏的契约或数据联动 |
| 4 | 制定技术方案 | 技术方案（B/C 类必须） | 分层落点明确、契约对齐、风险与回滚清楚 |
| 5 | 拆解实施步骤 | 原子步骤清单（每步可验证） | 步骤有顺序、有验证方式、无并行冲突 |
| 6 | 编写或修改代码 | 代码 + 按步骤提交 | 未偏离方案、无无关改动、五层合规 |
| 7 | 执行测试 | 测试证据（命令/范围/结果） | 相关用例实跑，高优先级全通过 |
| 8 | 检查是否符合验收标准 | 自检清单结论 | DoD 全部满足或已说明例外 |
| 9 | 更新相关文档 | 文档 diff | 行为变化已同步到权威文档 |
| 10 | 总结本次变更 | 变更总结 | 改动/影响/证据/遗留/回滚齐全 |

### 3.1 阶段 1 —— 明确任务目标和需求来源

**动作**：

1. 用一句话写清目标，必须可被验证（"完成 X 页面"不合格，"列表页支持茶类/产地/季节三维 AND 筛选并显示结果计数"合格）。
2. 标注需求来源，至少一条：
   - PRD 章节（功能分级、业务规则）；
   - API_CONTRACT 端点 + openapi.yaml 定义；
   - SECURITY 的安全项编号（S-xx）；
   - TEST_PLAN 用例 ID（如 AUTH-01）；
   - PAGE_SPECS / DESIGN_SYSTEM 章节（视觉与交互）；
   - AGENTS.md §13 的已知待办。
3. 写明范围外：本次**不**做什么。
4. 按 §2.1 判定并记录 A/B/C/D。
5. 写出可执行的验收标准（2–5 条），例如：
   - `GET /api/v1/teas` 带 `category` + `origin` + `season` 时返回 `code=0`，`data.total` 与数据库条件计数一致；
   - 无匹配时返回空数组而非 404；
   - 不产生任何写库操作。

**完成判据**：任务卡填完；任何一条验收标准都能对应到文档条款或测试用例。

**常见错误**：来源缺失却直接开工；验收标准写成"功能正常"；范围外留白导致顺手扩做。

### 3.2 阶段 2 —— 阅读相关项目文档

按任务类型读取下表列出的文档（其余文档按需）：

| 任务类型 | 必读文档与章节 |
|---|---|
| 后端端点实现 | [API_CONTRACT.md](../api/API_CONTRACT.md) 对应端点 + [openapi.yaml](../api/openapi.yaml)、[ARCHITECTURE.md](../architecture/ARCHITECTURE.md) §3/§5、[MODULE_DESIGN.md](../architecture/MODULE_DESIGN.md) 对应模块、[DATA_MODEL.md](../architecture/DATA_MODEL.md) 相关表、[SECURITY.md](../architecture/SECURITY.md) 相关 S 项、[TEST_PLAN.md](../testing/TEST_PLAN.md) 对应用例 |
| 认证/会话/权限 | PRD 认证与权限章节、[ARCHITECTURE.md](../architecture/ARCHITECTURE.md) §1.3、SECURITY 认证类安全项、API_CONTRACT `auth` 端点、TEST_PLAN AUTH/PERM 用例 |
| 收藏 / 清单 / 分享 | PRD 收藏与分享章节、API_CONTRACT `favorites`/`lists`/`shares`、SECURITY 越权项、TEST_PLAN FAV/LIST/SHARE 用例 |
| 管理员后台 | PRD 管理员章节、API_CONTRACT `admin` 端点、SECURITY 管理员门禁项、PAGE_SPECS 后台页、DESIGN_SYSTEM 后台组件约定 |
| 数据库/迁移 | [DATA_MODEL.md](../architecture/DATA_MODEL.md) 表定义、[init.sql](../../database/init.sql)、ARCHITECTURE §5.4、TEST_PLAN 数据库约束用例 |
| 前台页面/样式 | [PAGE_SPECS.md](../design/PAGE_SPECS.md) 对应页、[DESIGN_SYSTEM.md](../design/DESIGN_SYSTEM.md)、`原型/` 对应页面 |
| 测试代码 | TEST_PLAN 用例（步骤 + 断言 + 对应接口/安全项）、API_CONTRACT、SECURITY |
| 文档修订 | 目标文档的权威版本章节 + AGENTS.md §10，并交叉核对其引用文档 |

**完成判据**：能在任务卡中写出关键约束（如"分享撤销后 `HTTP status = code // 100`"、"前台禁用 Element Plus"、"色值禁止硬编码"）。

### 3.3 阶段 3 —— 分析现有代码和影响范围

先搜索再动手，禁止凭印象新增文件。分析结果按层填写：

| 区域 | 需要确认的问题 |
|---|---|
| `routers/` | 涉及哪些端点？是否只做参数接收与 `Depends` 注入？ |
| `services/` | 业务规则与事务边界是否落在此层？是否已有同名方法可复用？ |
| `repositories/` | 是否已有查询方法？新增方法放哪个文件？ |
| `models/` + `alembic/` | 是否触及表结构？有无迁移需求（有则为 C 类） |
| `schemas/` + 前端 `types/` | 字段、必填、长度、枚举是否与契约完全一致？ |
| `core/` | 响应封装、异常映射、鉴权依赖是否受影响？ |
| 前端 `api/` `stores/` `views/` | 请求路径、参数、错误处理、加载态与空态 |
| 测试 | 新增或需要重跑的 TEST_PLAN 用例 ID |
| 文档 | 阶段 9 需同步的文档清单 |

同时记录"**不改动的相邻逻辑**"，避免顺手重构。

**完成判据**：产出影响文件清单（新增/修改），并说明每处改动属于哪一层、对应哪个验收标准。

### 3.4 阶段 4 —— 制定技术方案

- **A 类**：可在任务卡写 3–5 行要点（改哪些文件、怎么做、怎么验证），无需完整方案文档。
- **B 类**：必须输出 §5.2 的完整方案。
- **C 类**：完整方案 + 变更影响说明 + 待确认问题，等待用户答复。

方案必须包含：目标与非目标、约束（引用文档条款）、分层落点、接口与数据变更（无则写"无"）、异常与安全处理、测试策略、风险与回滚。

**完成判据**：方案能回答"为什么这样分层"、"字段名与契约是否逐字一致"、"出错时返回什么 `code`"、"失败如何回退"。

### 3.5 阶段 5 —— 拆解实施步骤

把方案拆成原子步骤，每个步骤满足：可独立验证、改动文件可枚举、失败可单独回退。推荐顺序（后端改动时）：

```
① 数据库/迁移（如需，C 类）
② schemas（Pydantic DTO）
③ repositories（查询封装）
④ services（业务规则 + 事务）
⑤ routers（路由与依赖注入）
⑥ 前端 types → api 封装
⑦ 前端 stores / views / 样式
⑧ 测试用例（pytest / Vitest）
⑨ 文档同步
```

每个步骤写：`动作 | 涉及文件 | 验证方式`。步骤之间若存在强依赖，明确标注先后。

**完成判据**：步骤清单覆盖全部验收标准；不存在"最后一步才验证"的大块改动。

### 3.6 阶段 6 —— 编写或修改代码

**通用约束**：

- 严格按阶段 4 方案实施；偏离即回到阶段 4 说明原因。
- 只改任务涉及的文件；不重排无关代码、不改无关命名、不升级无关依赖。
- 保持文件既有风格；新增代码遵循同文件既有写法。

**后端**：遵守五层红线（AGENTS.md §5）——Router 不写业务、不直接查库、不返回 ORM；Service 不拼 SQL；Repository 不做业务判断；Schema 不 import Model。

**前端**：前台禁用 Element Plus；后台组件放 `views/admin/` 并动态 `import()`；颜色/字号/间距只用 CSS 变量；`types/` 与 Pydantic Schema 字段一一对应。

**契约**：JSON 字段 `snake_case`、空值 `null`、成功 `code=0` 且 HTTP 200、业务失败 `HTTP status = code // 100`、时间 UTC + ISO8601 带 `Z`。

**提交**：按原子步骤提交，message 形如 `feat: 实现茶品列表三维筛选` / `fix: 422 重映射为 400/40000`；不含密钥、密码、Cookie 值。

**完成判据**：代码自查无跨层、无硬编码色值、无无关 diff；每个原子步骤完成即跑最小相关测试。

### 3.7 阶段 7 —— 执行测试

| 类型 | 范围 | 要求 |
|---|---|---|
| 后端 API 测试 | pytest + httpx/TestClient，对应用例 ID | 断言 HTTP 状态码 + 业务 `code` + 数据库最终状态 |
| 数据库约束 | 唯一索引、外键、ENUM、软失效 | 至少覆盖本次改动涉及的表 |
| 前端单测 | Vitest，纯函数（筛选/格式化/URL 组装） | 改动纯函数必须有对应用例 |
| 手工冒烟 | 涉及页面的关键路径（登录 → 列表 → 详情 → 收藏 → 分享） | 记录操作路径与观察结果 |

**现状与前置条件**（进入开发前须知）：

- `backend/tests/` 已按模块落地 TEST_PLAN 用例（2026-11-09 全量 139 passed），前端 ESLint / Prettier / Vitest 脚本与 `.github/workflows/ci.yml` 已建立；新增业务代码须同步新增或补跑对应用例。

### 3.8 阶段 8 —— 检查是否符合验收标准

## 6. 例外流程

### 6.1 紧急修复（hotfix）

线上或阻断性缺陷可压缩阶段 2、4、5：只读直接相关文档 → 一句话方案 → 立即修复。但 **阶段 7 测试、8 验收、9 文档、10 总结不可省**；事后立即补记任务卡与变更记录。若修复需要动契约/表结构/安全校验，仍属 C 类，不得以"紧急"为由绕过确认。

### 6.2 调研/探索任务

只读代码与文档、给出结论，不产出业务代码。产出：结论、依据、可执行建议、待确认问题；不修改任何文件（除用户明确要求落盘调研文档）。

### 6.3 用户豁免

用户明确要求跳过某项测试或检查时，可以执行，但必须在 build-log 记录：**日期、豁免范围、原因、已知风险**。未记录的豁免视为未发生，交付结论仍按"未运行/未覆盖"处理。涉及契约、表结构、安全校验的 C 类变更不得豁免确认流程。

### 6.4 阻塞与升级

遇到契约缺失、文档冲突、外部依赖不可用：先按 AGENTS §10 核对权威版本；仍无法判定则停止实现，输出"冲突描述 + 影响 + 可选方案"，等待用户决定。**不得自行编造规则来解除阻塞。**
